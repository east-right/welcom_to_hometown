# Agentic vs Flow — 수치 비교

"단방향 flow보다 양방향 agentic이 낫다"를 **재현 가능한 수치**로 표현한다.
두 갈래로 잰다: ① agentic의 런타임 판단을 직접 계량 ② flow 시스템(v2)과 end-to-end A/B.

- 모델 통제: 양쪽 **`gemini-3.1-flash-lite`** 동일 (v2는 `WH_MODEL` 오버라이드로 맞춤).
- 테스트셋: `data/test.json` — 12케이스 / 정답 24개.
- v4 원자료 `experiments/eval_run.json`, v2 원자료 `logs/report_gemini-3.1-flash-lite_*.json`.

---

## 방법 1 — agentic은 "제어 흐름이 런타임에 결정된다"를 계량

flow는 정의상 **모든 질문이 같은 경로·같은 콜 수**여야 한다(제어권=코드).
agentic이면 중간 결과를 보고 경로가 갈라진다(제어권=모델). v4 실행의 실측:

| 지표 | v4(agentic) 실측 | 순수 flow라면 | 해석 |
|---|---|---|---|
| 재검색률 | **25%** (3/12) | 0% | 코드에 없는 collect_places/info 재실행 |
| 고유 실행경로 수 | **4** | 1 | 질문마다 경로가 갈라짐 |
| 툴콜 길이 | **4~6** (평균 4.4) | 상수 | "파는 깊이"가 질문마다 다름 |

런타임에 갈라진 3케이스(flow면 불가능한 행동):
```
창원 귀산 맛집   places→info→places→info…   한 바퀴 돌고 부족 판단 → 재수집
창원 가포 맛집   places→places→info…        첫 수집 보고 재수집
부모님 식당      places→read→places→info…   읽고 판단 후 재수집
```
→ "정보가 더 필요하면 스스로 툴을 재실행"이 **25% 빈도로 관측**. 이 테스트셋은 전부
식당/카페(=전부 recommendation)라 축제·장소 분기와 되묻기가 안 켜졌으므로 **25%는 하한**.

## 방법 2 — flow 시스템(v2) vs agentic 시스템(v4) end-to-end A/B

v2는 명시적 flow 엔진(`service_v2/main.py`: "앱은 하나의 하네스 flow다 … 전부 검색을
코드가 보장, 모델은 쿼리분해·선택만"). 같은 테스트셋·같은 모델로 최종 recall 비교.

| 지표 | v2 (flow) | v4 (agentic) | 차이 |
|---|---|---|---|
| **정답단위 recall(최종)** | 8.3% (2/24) | **50.0%** (12/24) | **+41.7p** |
| **케이스단위 recall** | 16.7% (2/12) | **91.7%** (11/12) | **+75.0p** |
| MRR | — (미측정) | 0.510 | — |
| 평균 추천 카드수 | 5.9 (0~10) | 5.3 (4~8) | 비슷 |

**카드 수가 비슷**(5.9 vs 5.3)하므로 격차는 "많이 뿌려서 이긴" 착시가 아니다.
오히려 v2는 한 케이스에서 카드 0개(부대찌개)로 무응답이 나오기도 했다.

케이스별 (matched/정답, 추천카드수):
```
질문                              v2(flow)      v4(agentic)
창원 귀산 바다 커피 맛집            0/4 (4장)     1/4  ✅
신림역 혼밥 식당                   0/1 (9장)     1/1  ✅
창원 귀산 맛집                     1/2 (10장)    1/2  ✅
창원 가포 맛집                     0/4 (10장)    1/4  ✅
마산 합성동 피자                   0/1 (3장)     1/1  ✅
창원 횟집                          1/3 (7장)     0/3  ❌ (둘 다 약점)
신림역 칼국수                      0/1 (3장)     1/1  ✅
신림역 부대찌개                    0/1 (0장!)    1/1  ✅
신림역 고기집                      0/3 (4장)     1/3  ✅
신림역 감성 카페                   0/2 (7장)     2/2  ✅
신림역 횟집                        0/1 (6장)     1/1  ✅
신림역 부모님 식당                 0/1 (8장)     1/1  ✅
```

## 범위와 한계 (정직하게)

이 A/B는 **단일 변수(agentic 루프)만 격리한 게 아니라** v2·v4 두 시스템 전체를 비교한다.
v4는 flow가 아니라는 것 외에도 **웹수확·HyDE 임베딩 리랭크** 등 수집·랭킹이 v2보다 낫다.
따라서 +41.7p/+75.0p는 **"과거 flow 시스템 → 현재 agentic 시스템" 전환의 총효과**이며,
이 중 순수 agentic 루프의 기여분은 방법 1(재검색 25%)이 하한을 보여준다.

- **순수 단일변수 격리가 필요하면**: v4에서 재검색 루프만 끈 "단일패스 v4"를 만들어
  같은 수집·리랭크 위에서 A/B하면 agentic 루프의 순효과만 분리된다. (후속 과제)
- **분기·되묻기까지 계량하려면**: 테스트셋에 축제/장소 케이스를 추가해 collect_context
  분기와 too_broad 되묻기를 켜야 방법 1의 25%가 실제 값으로 올라간다.

## 재현
```bash
# flow(v2)
WH_MODEL=gemini-3.1-flash-lite WH_MAIN_MODEL=gemini-3.1-flash-lite \
  python -m poc.service_v2.eval.benchmark report --testset data/test.json
# agentic(v4)
cd poc/service_v4 && python eval.py -o experiments/eval_run.json
```
