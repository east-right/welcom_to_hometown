# collect_places 단계별 실험 기록

`collect_places`를 카카오 base로 축소한 뒤, 소스를 하나씩 붙이며 recall이 어떻게
변하는지 측정한다. 각 단계는 커밋으로 남겨 언제든 되돌릴 수 있게 한다.

## 측정 방법

- **테스트셋**: `test.json` (12케이스 / 정답 24개)
- **경유**: 질문을 `Chat`(에이전트)에 입력 → LLM이 스스로 `collect_places`를 호출 →
  그때 나온 풀을 기준으로 측정한다. (검색어를 손으로 넣어 툴을 직접 호출하지 않는다.
  자연어→검색어 압축 품질까지 포함해서 재기 위함.)
- **지표**
  - `Recall@수집` — 정답이 `collect_places` 풀 안에 있나 (검색어/소스 커버리지 문제)
  - `Recall@최종` — 정답이 최종 추천에 있나 (랭킹/선별 문제)
  - `MRR` — 최종 추천에서 첫 정답의 순위
- **원자료**: 각 단계의 `experiments/*.json` (eval.py 출력 전체)

## A. baseline (kakao only) — 관찰

1. **자르기(`_refine`→15) 제거만으로 Recall@수집이 62.5% → 83.3% (+20.8p).**
   이전 파이프라인은 소스를 더 썼는데도(fanout+다이닝코드) 풀을 15개로 잘라
   순위 밖 정답을 버렸다. 넓게 남기니 수집 recall이 크게 올랐다.
   → 자르기의 위치가 잘못됐던 것. "수집 직후"가 아니라 "좋은 랭킹 뒤"여야 한다.

2. **대신 Recall@최종·MRR은 소폭 하락** (33.3→29.2 / MRR .322→.271, 케이스 66.7→50.0).
   풀이 커지면서 정답이 더 깊이 묻히고(귀산옥 35위, 푸른회전문 27위, 본화로 13위),
   최종 5~8개 선별이 더 어려워졌다.
   → **병목은 "수집"이 아니라 "랭킹/선별"** 임을 재확인. 다음 목표가 여기임.

3. **비용 상승**: tok_in 217k → 257k. 자르기 없이 ~45곳을 `collect_info`로 넘기니
   크롤링·요약이 늘었다. → 넓은 수집은 공짜가 아니다. 랭킹 뒤 자르기로 되돌려야 함.

4. **kakao만으론 못 잡는 정답 4개** (검색어/소스 커버리지 한계):
   - 개성순대, 우동한그릇 (창원 가포) ← 다이닝코드가 복구하던 매장
   - 거영수산in해녀의집 (창원 횟집)
   - 정담은보쌈 (신림역 부모님 식당) — 카카오엔 "정담은보쌈 신림점"으로 있는데 미매칭
   → 다음 단계(업종확장 / 클린 다이닝코드)에서 이들이 돌아오는지로 소스 효과 측정.

## B. 수확 보강 (kakao + 웹스니펫 LLM 수확) — 관찰

정규식 다이닝코드 파서(지역명 하드코딩)를 삭제하고, **네이버 웹검색 스니펫 →
LLM으로 상호명만 추출 → 카카오 역조회로 실존/주소 확보 → 같은 구만 병합**으로 교체.
웹 쿼리에 `Top`을 붙여 랭킹 리스트 페이지(로컬 매장이 촘촘한)를 노림. 지역명 하드코딩 없음.

1. **Recall@수집 83.3 → 95.8% (정답), 91.7 → 100% (케이스).** 수집 miss가 4개→1개.
   되살린 매장: 개성순대·우동한그릇(가포 목표) + 등대집·정담은보쌈·거영수산.
   → kakao만으론 못 잡던 로컬 노포를 수확이 메움. **수집 천장 확보.**

2. **우동한그릇 진단**: 일반 쿼리('창원 가포 맛집' d=30) 스니펫엔 미등장 →
   `Top` 부착(또는 d=50↑)하면 랭킹 리스트 페이지가 걸려 등장. 카카오엔 실존
   ('경남 창원 마산합포구 가포로 706')하므로 역조회는 성공. 이름을 스니펫에서
   못 건네주던 게 원인이었고, `Top` 바이어스로 해결.

3. **최종·MRR은 정체/하락** (MRR .271→.232, 케이스 최종 50→41.7%). 풀이 커지고
   (거영수산 64위, 뜨라또리아 27위) 정답이 깊이 묻혀 최종 5~8 선별이 더 어려워짐.
   → **병목은 온전히 랭킹/선별.** 리랭킹(D)의 몫으로 넘어감.

4. **비용/시간 ⬆️** (26.7→46.4초, tok_in 257k→306k). 수확이 naver 1 + llm 1 +
   `verify_names`의 순차 카카오 역조회(~50건)를 더함. 순차 역조회가 지연의 주범 —
   병렬화 여지 있음(나중).

5. **남은 수집 miss 1개**: 귀산옥 해물칼국수 (창원 귀산). 개별 진단은 보류.

## C. HyDE 리랭크 (블로그 스니펫 기반) — 관찰

`collect_info`를 재구성: 블로그 검색(전체)로 스니펫만 확보 → **HyDE 리랭크**로 상위 15만
남기고 → 크롤링·요약은 그 15만. HyDE = 요청에 맞는 '이상적 리뷰'를 LLM으로 한 편 생성해
임베딩하고(질문 문장이 아니라), 각 매장 블로그 스니펫과 **최대(max) 유사도**로 정렬.
임베딩 모델 `gemini-embedding-001`(768차원), 리랭크 근거는 `info_rerank` 파일에 전량 기록.

1. **케이스단위 최종 41.7 → 75.0%, MRR .232 → .531 (×2.3).** 정답을 찾으면 훨씬 상위에
   놓는다. **목표("45→리랭킹 15에서 70~80%")를 케이스단위로 명중.**

2. **비용·시간 동반 하락** (tok_in 306k→218k, 46.4→38.5초). 크롤링·요약 대상이 66→15로
   줄어든 효과. 임베딩(768차원, 100개 배치 ~2초)·HyDE 생성 1콜의 추가분보다 절감이 크다.
   → **리랭크가 비용을 더하는 게 아니라 깎는다**는 가설 그대로.

3. **스니펫은 변별력이 약하다(사용자 의심이 옳음).** 리랭크 점수가 대부분 0.66~0.74에
   뭉친다. 블로그 스니펫이 죄다 "○○ 맛집 다녀왔어요~" 마케팅 인트로라 가상리뷰와
   비슷하게 나온다. 그 결과 **깊이 파묻힌 수확전용 노포는 못 건져올림**:
   개성순대(리랭크 후 46위), 우동한그릇(52위), 거영수산(64위) → 정답단위 최종은 제자리(41.7%).

4. **HyDE는 구체 쿼리엔 강하고 막연한 쿼리엔 독.** '창원 가포 맛집'처럼 조건이 없으면
   HyDE가 '바다 풍경·부모님·해물정식' 같은 없는 조건을 지어내 편향시킨다. 반대로
   '부모님 모시고', '혼밥', '감성 카페'처럼 조건이 분명한 케이스에서 이득이 크다.
   → gapo(다중 정답·막연)만 4/4→2/4로 퇴행, 나머지 구체 케이스가 총합을 끌어올림.

5. **다음 갈림길**:
   - (a) **소스 quota** — 수확전용 매장에 top-15 중 몇 자리 예약(파묻힘 방지). LLM 0.
   - (b) **본문 기반 리랭크로 승격** — 스니펫 대신 크롤링 본문 임베딩(변별력↑, 비용↑).
   - 먼저 (a)로 노포를 구조적으로 건지고, 부족하면 (b) 검토.

## D. 2단 깔때기 (스니펫 필터 → 본문 리랭크) — 관찰 (회귀, 방향 폐기)

C의 "스니펫은 변별력 약함"을 본문으로 풀려는 시도. 1단은 스니펫 HyDE로 ~25개까지
관대하게 추리고(수확 노포 전량 보존), 2단은 그 25곳의 블로그 본문을 크롤·임베딩해
가상리뷰와 유사도로 정밀 정렬 → 상위 15. 본문은 요약에도 재사용.

1. **본문 임베딩이 스니펫과 사실상 동일.** 본문 점수 vs 스니펫 점수 차이 =
   **평균 0.0038, 최대 0.057 (n=288).** 비싼 본문 크롤이 변별력을 0 추가했다.

2. **C보다 회귀** (MRR .531→.306, 케이스최종 75→50%). 본문이 변별을 못 하니, 남은 건
   flat 점수로 두 번 자르는 것(75→25→15)뿐 → 한 번 컷(C)보다 정답을 더 잃음.

3. **핵심 결론 — 임베딩 코사인(bi-encoder)은 이 데이터에서 근본적으로 flat(~0.70).**
   스니펫이든 본문이든 한국어 맛집 후기끼리 다 비슷하게 임베딩돼 변별이 안 된다.
   → **HyDE 임베딩 리랭크 방향은 폐기.** 코드는 C로 되돌린다.

4. **다음 방향 (변별이 필요하면 조인트 판단으로)**:
   - **cross-encoder** — 질문·후보를 함께 넣어 어텐션으로 연관도 산출(bi-encoder 코사인과
     다름). 임베딩이 못 하는 미세 변별 가능. 로컬 다국어 모델이면 추론 무료.
   - **LLM-judge 리랭크** — 후보 메타+스니펫을 한 프롬프트에 넣고 LLM이 읽고 순위. 조인트
     추론이라 코사인 한계를 넘음. util-LLM 소수 콜.
   - **구조적 quota** — 변별에 의존하지 않고 수확 노포에 자리를 예약(파묻힘 방지).
   - 별개 문제로, 랭킹실패의 ~40%는 **최종 답변 LLM이 리랭크 상위를 무시**(목포수산 리랭크
     1위인데 탈락). INSTRUCTION이 rerank_score를 안 쓰기 때문 → 프롬프트에 반영 필요.

## 단계별 funnel 측정 도입 (eval.py) + C·E·F 재해석

eval.py에 4단계 funnel(수집/1차필터/리랭크/최종) 측정을 추가. 이걸로 C·E·F를 나란히
보니 결정적 사실이 드러남:

**리랭크 단계가 C·E·F 전부 62.5%(15/24)로 동일하다.** 스니펫 HyDE 임베딩으로는 어떻게
구성하든(필터 유무, 본문 유무, HyDE 버전) 15/24가 천장. 세 버전의 최종 지표 차이(MRR
.53/.46/.30)는 **거의 전부 "최종 답변 LLM" 단계의 노이즈**다 — 리랭크 top-15에서 5~7개를
비결정적으로, rerank_score를 무시한 채 버리기 때문. → **단일 실행으로 리랭크 방식을 비교한
건 사실상 최종 LLM 노이즈를 비교한 것.** 진짜 레버는 둘로 좁혀짐:
- **① 최종 답변 LLM (−5~−7)** — 리랭크 상위 무시. INSTRUCTION에 rerank_score 미반영. 최대 누수.
- **② 리랭크 천장 62.5%** — 스니펫 임베딩 한계. 넘으려면 cross-encoder/LLM-judge or keep>15.

## F. 스니펫 리랭크 + 새 HyDE + 협찬 — 관찰

C 구조(사전 필터·본문 임베딩 없이 전량 스니펫 랭킹)에 새 HyDE + 협찬 필터(최종 요약에만)를
얹음. 가장 단순·저렴(본문 크롤 랭킹 없음).
1. **리랭크 62.5%(15/24) — C·E와 동일.** 최종은 33.3%(8/24)로 이 실행에선 낮게 나옴(최종
   LLM이 −7). MRR .299. → F가 C보다 "나쁘다"기보단 **최종 LLM 단계 변동성**이 큼.
2. **구조는 F가 가장 깨끗** — 깔때기·본문 임베딩(redundant) 제거, 협찬 필터·새 HyDE 유지.
   리랭크 결과가 같으니 F의 단순함이 이득. 다음 개선(최종 LLM)의 베이스로 적합.

## G. LLM-judge 리랭크 — 관찰 (임베딩 천장 돌파)

F 구조에서 리랭커만 임베딩 코사인 → **LLM-judge**로 교체. 후보(상호명·카테고리·블로그
후기제목)를 통째로 한 프롬프트에 넣고, 요청에 맞는 top-15를 순위로 고르게 함(util-LLM 1콜).
HyDE·임베딩 제거.

1. **리랭크 top-15가 62.5% → 75.0%로 돌파.** C·E·F 임베딩이 전부 62.5%에 막혀 있던
   천장을 넘음. 개성순대(수집 48위)를 리랭크 4위로 끌어올리는 등, 코사인이 못 하던
   '요청↔매장' 추론 변별을 함. → **"top-15 천장은 슬롯이 아니라 랭커 탓"이 확증됨.**

2. **Recall@최종(정답) 58.3% — 역대 최고** (임베딩 33~42%). MRR .491.

3. **남은 누수 셋** (funnel: 수집 95.8 → 1차필터 83.3 → 리랭크 75 → 최종 58.3):
   - **1차필터 −3**: 창원 횟집 되묻기(question) — 리랭커 무관, 구조적.
   - **리랭크 −2**: 뜨라또리아·목포수산을 judge가 top-15에서 놓침. (후기제목만으론 부족)
   - **최종 LLM −4**: 블루피쉬·더로드101·등대집·정담은보쌈 — 리랭크 통과했는데 최종 답변
     LLM이 버림. rerank_rank 미반영.

4. **다음 레버**: ① 되묻기 케이스 진행(+3, 구조적) ② 최종 LLM이 리랭크 존중(−4) ③ judge
   입력에 후기 본문/카테고리 더 주면 리랭크 −2도 회수 여지.

## E. HyDE 수정 + 협찬 필터 — 관찰 (D의 두 confound 제거)

D 회귀의 원인이 "임베딩 한계"가 아니라 두 confound(HyDE 창작 + 협찬 노이즈)일 수 있다는
가설로, 둘을 제거하고 재측정.
- **HyDE 프롬프트 수정**: 쿼리에 명시된 조건만 반영, 없으면 창작 금지. gapo 가상리뷰가
  "해물정식·부모님·바다뷰"(창작) → "가포 맛집 만족스럽게 먹음"(담백)으로 바뀜.
- **협찬 필터**: 크롤 본문의 첫 사진이 비네이버(레뷰·리뷰노트 등)면 협찬으로 보고 제외.
  `scrape_urls`가 `sponsored` 플래그 반환, collect_info가 임베딩·요약에서 제외.

1. **D 대비 대폭 회복** (MRR .306→.461, 케이스최종 50→66.7%). gapo 0/4→**3/4**
   (우동한그릇 1위·개성순대 2위·등대집 3위). 가상리뷰 점수도 답들이 0.80~0.82로 뜨고
   비답이 하위로 갈림 → **변별이 생김.** → 확정: **D의 flat은 임베딩 한계가 아니라
   "엉뚱한 HyDE + 협찬 노이즈" 탓이 컸다.** (앞서의 "임베딩 폐기" 결론은 성급했음)

2. **협찬 필터 실효**: gapo에서 크롤 37건 중 10건이 협찬으로 제외됨. 마케팅 카피 감소.

3. **단, 여전히 C(.531)보다 약간 아래** (E .461). 이유 둘: (a) 본문≈스니펫이라 2단 본문
   임베딩은 여전히 redundant, (b) 필터 2단(75→25→15)의 손실. 게다가 C는 옛 HyDE라
   **공정 비교가 아님**(C에 새 HyDE를 안 먹임).

4. **다음 정리 수순**: 이기는 재료(faithful HyDE + 협찬 필터)는 확정. 본문 임베딩 funnel은
   redundant이므로, **C 구조(단일 스니펫 리랭크)에 새 HyDE + 협찬 필터를 얹어** 비교하면
   가장 싸고 깔끔한 최선 후보. 단 협찬 필터는 크롤이 있어야 동작(스니펫엔 이미지 정보 없음)
   → 크롤을 "협찬 판정 + 요약"용으로만 쓰고 랭킹은 스니펫으로 하는 절충이 유력.
